## 诊断 CRSF(rc_channels) 全 0、串口回调 length=0 —— 代码改动已回退

> 下面内容仅作排查结论存档，代码现状仍是"有 bug 的版本"。

### 现象
`rc_channels.ch[]` 一直为 0；`crsf_rx_idle_callback` 一进入 `crsf_rx_msg_check` 就因 len=0 退出。

### 排查结论（两处缺陷）
1. `User_Files/1_Middleware/Driver/CRSF/crsf.cpp:37`
   `crsf_rx_msg_check(const uint8_t *msg, const uint8_t len)` 形参是 **uint8_t**，
   而调用方传入 uint16_t 的 `length`。一旦 length ≥ 256（DMA 半传输 HT=256 / 满传输 TC=512）
   就被截断成 0 → `len < 4` 直接 return。改法：`uint16_t len`。
2. `User_Files/1_Middleware/Driver/UART/drv_uart.cpp` 的 `HAL_UARTEx_RxEventCallback`
   不区分事件类型。HAL 的 ReceiveToIdle + Normal DMA 会额外上报 HT(Size=256)/TC(Size=512)，
   上层被当成"一帧"处理必然解包失败；且 HT 时 RxState 仍为 BUSY_RX，
   里面调用的 `HAL_UARTEx_ReceiveToIdle_DMA` 会静默返回 HAL_BUSY，双缓冲指针与 DMA 实际
   写入的 buffer 错位。改法：在 `init_finished` 判断之后统一过滤，
   非 `HAL_UART_RXEVENT_IDLE` 直接丢弃；仅当 RxState 为 READY（TC 场景）时用 `UART_Reinit()` 重启。

### 附带发现（未修）
`MX_UART7_Init()`（HAL_UART_Init 内部已使能 RE）到 `Task_Init()` 末尾才调用 `UART_Init()`
之间这段窗口收到的字节会残留在 RDR 并置位 ORE，造成首帧错位 + DMA 一启动就进错误中断。
改法：`UART_Init`/`UART_Reinit` 开头清 ORE/PE/FE/NE + `UART_RXDATA_FLUSH_REQUEST`。

### 排查中已排除的项
- D-Cache / MPU 未启用，不是 cache 一致性问题
- `.ram_d2` 未被清零 —— 不成立，startup_stm32h723xx.s 已对 `_sram_d2` 做清零
- RAM_D2 占用 10688B / 32K，没有溢出
- UART7_IRQHandler、DMA1_Stream3_IRQHandler 接线正确；中断优先级 5 与 FreeRTOS 配置不冲突

### 待用户确认的硬件侧
- UART7 RX(PE7) 配成 `GPIO_NOPULL`，接收机未上电/未对频时引脚浮空会产生连续噪声帧，
  线路永不安静 → 只触发 HT/TC 不触发 IDLE。建议改 `GPIO_PULLUP`
- 确认接收机已对频、输出为 420000 波特非反相 CRSF
